# Disposable WebDAV mutation qualification

This experiment checks whether one real WebDAV server preserves reviewed files during conditional mutations and failures. It never contacts a NAS: the server binds to `127.0.0.1`, and every file is generated inside a temporary directory. It does not exercise the Apple app's HTTPS or authentication code.

```sh
python3 -m venv /tmp/gumbo-dav-fixture
/tmp/gumbo-dav-fixture/bin/pip install 'WsgiDAV==4.3.3'
/tmp/gumbo-dav-fixture/bin/python Tools/WebDAVWriteFixture/probe.py
```

Run from the repository root. Exit zero means the experiment completed, **not** that the server qualified. Read `qualifies_for_generic_reviewed_mutations` in its JSON output. This is an opt-in experiment with a separate development dependency, not a production dependency or ordinary package test.

## Observed on 2026-09-21

WsgiDAV 4.3.3's filesystem provider, Python 3.9.6, macOS 27.0 arm64:

| Operation | Actual result |
| --- | --- |
| OPTIONS | DAV `1,2`; DELETE and MOVE advertised |
| DELETE with a stale `If-Match` | HTTP 412; original preserved |
| MOVE with a stale tagged destination `If` condition | HTTP 204; original overwritten |
| Same-length external rewrite with original modification time restored | Bytes changed; ETag unchanged |
| Injected final provider MOVE failure | HTTP 500; original absent; staging file retained |
| External path replacement injected immediately before provider unlink | HTTP 204; replacement deleted |

The last two are deterministic fault/interleaving injections into the actual provider methods, not claims that a spontaneous race or disk failure occurred. They demonstrate boundaries that Gumbo cannot infer from `DAV`, `Allow`, a quoted ETag or a successful ordinary DELETE. The same-stat test changes only generated bytes and restores their timestamp deliberately. These results apply to this tested implementation/configuration; they do not establish the behavior of every WebDAV server.

**Decision:** this server does not qualify. Gumbo continues to advertise WebDAV and SMB as read-only native providers. The separately configured metadata helper permits supported tag edits only. No generic delete/replace capability is enabled by this experiment, and issue #196 remains open for a provider with proven behavior.

## Protocol basis and future gate

HTTP `If-Match` requires strong comparison before a method proceeds. WebDAV's `If` header can associate conditions with named resources, while MOVE describes the source/destination operation. These rules do not establish an indivisible filesystem compare-and-replace transaction with another process accessing the same NAS files. See [RFC 9110 §13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1), [RFC 4918 §10.4](https://www.rfc-editor.org/rfc/rfc4918.html#section-10.4), and [RFC 4918 §9.9](https://www.rfc-editor.org/rfc/rfc4918.html#section-9.9).

SMB's rename request has `ReplaceIfExists`, and rename/disposition operations require DELETE access. That alone is not a condition comparing the destination against the version the user reviewed. A future implementation needs a demonstrated handle/locking and replacement policy across relevant writers; this fixture does not validate SMB writes. See Microsoft's [FileRenameInformation for SMB2](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/52aa0b70-8094-4971-862d-79793f41e6a8) and [SMB2 file-information handling](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/43cf22fe-84cb-49cf-b3e7-e3d7d766a7b7).

Before enabling a native provider, establish meaningful version identity, destination conditions, failure preservation, concurrent-writer behavior and acknowledged results on its actual supported configuration. Retain Gumbo's host/profile/source authorization, exact reviewed file paths, non-recursive operations and partial-result handling. An unknown result must not become an automatic repeat or a claim of successful deletion.
